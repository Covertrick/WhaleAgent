# 可靠执行：版本条件与故障注入

这组实验不调用模型。200 个场景来自 10 类故障、每类 20 个固定种子。种子只改变编号，不改变判定。复现命令：

```bash
python -m unittest tests.harness.test_fault_matrix -v
```

## 写入条件

`judge_write` 同时看来源修订和目标修订。

- 来源修订和读取时不一致：拒绝，不提交旧值。
- 目标在同一个 Vault 里，内容哈希变了：拒绝覆盖，也不另写一份。
- 来源在 Vault、提醒在调度器：检查通过之后，提交窗口里如果又变了，记为 `residual_race`，不把这次写成成功。这不是跨系统的原子提交。

不可逆写入前，EGAA 可以挂上 `revision_probe`。探针上的修订和信念里的修订不一致时，策略停在 `REVISION_CONFLICT`，不发出提醒。

同一个 `operation_id` 再调用 `create_task_with_reminders` 会返回已经存在的任务，不插入第二条。

## 200 次注入

| 编号 | 注入 | 观察到的行为 |
|------|------|----------------|
| F01 | 来源修订仍是 v1 | 允许提交 |
| F02 | 读取后变成 v2 | 拒绝旧值 |
| F03 | 跨系统提交窗口里又变了 | 20 次都记为剩余竞态，没有提交 |
| F04 | 回执是 UNKNOWN 后再用同参数调用 | handler 只有一次 |
| F05 | STARTED 之后、dispatch 之前崩溃 | 恢复后的同参数调用不再执行 |
| F06 | handler 已成功，效果还没记上就崩溃 | handler 一次；恢复后不再执行 |
| F07 | 列表里有同名、另一个 operation_id | 不把它当成这次成功 |
| F08 | 两个请求用同一个 operation_id | 任务记录只有一条 |
| F09 | 同一次 Run 恢复两次 | 第二次不追加通知，也不增加写入 |
| F10 | 查询返回网络错误 | 不把 UNKNOWN 改成成功 |

汇总：重复不可逆效果 0，未经授权写入 0，已知版本冲突后的旧值提交 0，把 UNKNOWN 标成成功 0。需要保持 UNKNOWN 的 120 个场景都保持了 UNKNOWN。

这只说明这 200 个预定义场景里没有看到不安全重复。不能写成生产环境在所有故障下都不重复。
